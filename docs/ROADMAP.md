## §0. Резюме

**Respo** — десктопное приложение (Windows → позже macOS) для адаптивной веб-разработки:
одна страница в N девайс-вьюпортах одновременно, с синхронизацией взаимодействий,
DevTools на девайс, честной CDP-эмуляцией и инструментами дизайнера. Улучшенный клон
Responsively App, написанный с нуля (их AGPL-код не используется). Полный паритет
функционала — одной большой фазой по утверждённой спеке; перед реализацией — выбор
дизайн-системы по сгенерированным концептам и спайк главного риска (R1, WebContentsView).

Стек и правила — [`../CLAUDE.md`](../CLAUDE.md). Карта документации — [`README.md`](README.md).

## §1. Текущее состояние (инвентарь)

- Кодовой базы ещё нет — только документация. Репозиторий: `https://github.com/prodbyEDDY/respo.git`, ветка `main`.
- Утверждённая спецификация: [`superpowers/specs/2026-08-28-respo-design.md`](superpowers/specs/2026-08-28-respo-design.md) (архитектура, полный каталог функционала ~90 фич, безопасность, риски, перф-бюджеты, тесты).
- Проведён полный разбор исходников Responsively App (функционал + источники лагов); выводы вшиты в спеку. Клон референса лежит в scratchpad сессии, в репозиторий не входит и входить не должен (AGPL).
- Команды проверки (`npm run dev/typecheck/test/e2e/build`) — заявлены спекой, окружение ещё не создано, **не проверены**.
- Известный техдолг: нет — проект чист; главный открытый риск — R1 (джиттер WebContentsView, спека §9a).

## §2. Архитектурные принципы

1. **Производительность — инвариант:** rAF-коалесинг вместо пер-событийных IPC, батчи событий, очередь скриншотов, виртуализация вьюшек. Источники лагов референса не воспроизводить.
2. **CDP-first:** всё «браузерное» (эмуляция, скриншоты, инспект, ввод) — через один debugger-аттач на view; никаких инжектируемых клиент-скриптов и локальных серверов.
3. **OSS-first:** готовые проверенные блоки (MIT/Apache/BSD/ISC); свой код — только для ядра (ViewManager, SyncEngine, оркестрация раскладок). GPL/AGPL запрещены.
4. **Безопасность браузера:** sandbox + contextIsolation везде, валидация входных URL, разрешения «спрашивать по умолчанию» (спека §7a).
5. **Типизированные границы:** все IPC-контракты в `src/shared/ipc.ts` (hub-файл координатора).
6. **Doc-as-code:** документация меняется вместе с кодом.

## §11. Журнал решений

### 2026-08-28 — W1 «Foundation» принята и смержена
**Контекст:** 8 задач W1 исполнены Opus-агентами (сгруппированные диспатчи), финальное ревью всей ветки нашло 1 критикал + 5 важных, фикс-волна закрыла все (ALL ADDRESSED).
**Решение:** волна принята; риск R1 снят на Plan A (rAF-батчи из renderer, цифры в отчёте волны); пер-таск ревью отключены по решению владельца (скорость) — остаются самопроверка исполнителя + финальное ревью ветки. UX-приоритет владельца (простота/чистота/интуитивность) — обязательный критерий всех UI-задач.
**Причина:** метрики в бюджете, тесты зелёные, секьюрити-инварианты §7a выполнены.
**Последствия:** follow-ups в [отчёте W1](progress/W1-foundation-2026-08-28.md); следующий шаг — план W2 (SyncEngine + сьюты/Device Manager).

### 2026-08-28 — Дизайн-система утверждена; старт реализации (W1)
**Контекст:** владелец выбрал финальный референс (скриншот-концепт «Light Studio») и принёс токены Family Style Reference.
**Решение:** дизайн-система = токены Family (палитра, inset-борды, радиусы, Inter) без сторибук-элементов; тёмная тема выведена и обязательна; всё UI — shadcn; анимации лёгкие (transform/opacity 120–180ms). Написан план W1 «Foundation», реализация — Opus 5-агентами под ревью координатора.
**Причина:** утверждённый визуал + требование владельца «всё на shadcn, обе темы, топ-производительность».
**Последствия:** [`design/DESIGN-SYSTEM.md`](design/DESIGN-SYSTEM.md) — обязательный контекст для всех UI-задач; спайк R1 вшит в Task 4 плана W1.

### 2026-08-28 — Система координации проекта (/lead + docs)
**Контекст:** спека утверждена, проект переходит от планирования к подготовке реализации; подключён GitHub-репозиторий.
**Решение:** создан слой управления: `CLAUDE.md`, `docs/README.md`, этот ROADMAP, `docs/prompts/` (шаблоны), `docs/progress/`, слэш-команда `/lead`.
**Причина:** единый источник правды и повторяемый процесс постановки/приёмки задач.
**Последствия:** статусы работ живут здесь (§10); журнал решений — здесь (§11); remote `origin` = github.com/prodbyEDDY/respo.

### 2026-08-28 — Ревью-проход по спеке
**Контекст:** проверка спеки на пропуски перед стартом.
**Решение:** добавлены секция безопасности (§7a), реестр рисков (§9a, главный — R1 джиттер WebContentsView), механика зума, общая сессия `persist:respo`, честные пределы синхронизации, локальные favicon, лимит истории, DPR-опция скриншотов, «Открыть файл…», измеримый перф-бюджет, английский язык UI.
**Причина:** спека молчала о главных технических и безопасностных рисках.
**Последствия:** SPIKE-R1 обязателен до основной разработки.

### 2026-08-28 — Полный паритет сразу; OSS-first; shadcn + Heroicons
**Контекст:** выбор этапности и подхода к UI.
**Решение:** один большой план на весь функционал референса (без MVP-фазы); максимум готовых OSS-блоков (каталог устройств — из Chromium, BSD); UI — shadcn/ui с кастомной темой + Heroicons.
**Причина:** запрос владельца; скорость разработки через проверенные компоненты.
**Последствия:** дизайн-система выбирается до плана реализации (DESIGN-01 → PLAN-01).

### 2026-08-28 — Electron (WebContentsView), с нуля, без кода Responsively
**Контекст:** старт проекта; референс Responsively App (Electron + `<webview>`, AGPL-3.0) сильно лагает.
**Решение:** писать с нуля на современном Electron (WebContentsView + CDP), Tauri отклонён; код и данные референса не использовать (AGPL), лицензии зависимостей — только MIT/Apache/BSD/ISC.
**Причина:** лаги референса — архитектурные (`<webview>`, нетроттленный IPC, browser-sync-сокеты); Tauri ломает DevTools/CDP-функционал и будущий macOS; AGPL заражает кодовую базу.
**Последствия:** архитектура зафиксирована в спеке §4; правила лицензий — в CLAUDE.md.
